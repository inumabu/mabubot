# 📝 コメント記述ルール

まぶBotのコメントは、コードの逐語説明ではなく、**責務・境界・契約・制約・互換性の理由**を残すために使います。公開10コマンドと旧Command実装の統合境界を特に明示します。

## 🎯 基本ルール

1. **1ファイル1要約**
   - TypeScriptファイルは先頭に1行のモジュールコメントを置きます。
   - レイヤー名と、そのファイルが担う責務だけを書きます。

2. **1ブロック1目的**
   - コメントは「なぜ必要か」「何の契約を守るか」のどちらかに絞ります。
   - 同じ内容をファイル・関数・クラスの3か所へ繰り返しません。

3. **コードから明白な処理は書かない**
   - 単純な `if`、代入、ループ、`return` の説明は禁止です。
   - 「配列を回す」「値を返す」などの逐語説明も不要です。

4. **現在の仕様を書く**
   - コメントは現在の挙動・契約を記述し、予定や願望はTODOへ分離します。

5. **日本語＋必要最小限の絵文字**
   - 絵文字はモジュールの役割や重要な境界を示すときだけ先頭に1つ使います。
   - 同じ種類の処理では同じ絵文字を使います。

## 🧩 統合ルーター `src/core/client/command-aggregate.ts`

ここでは次の3点だけを重点的にコメントします。

- 🔗 公開routeと旧Commandの対応
- 🔄 旧CommandのJSON/Option定義を統合Builderへ復元する理由
- 🛡️ Discord.js Builder / callback契約を守る箇所

業務ロジックの説明は旧機能側へ書き、統合ルーターには書きません。

## 🔁 旧Command実装の互換層

互換層のコメントは「旧機能をどう動かすか」ではなく、**なぜ旧実装をそのまま再利用する必要があるか**を残します。公開Helpに置き換えた旧Help実装は互換層として扱わず、置換済みであることを明記します。

- 🚫 業務ロジックを追加しない
- 🚫 DBを直接操作しない
- 🚫 UI文言を互換層で変更しない
- ✅ 旧Commandが期待する入力契約だけを維持する
- ✅ 旧Handlerを段階移行できるようにする

## 📦 各レイヤー

| レイヤー | コメントする内容 | コメントしない内容 |
| --- | --- | --- |
| 公開Command | 公開入口と束ねる領域 | 各subcommandの読み上げ |
| Service | 非自明な業務ルール・Transaction | 各関数の入出力の読み上げ |
| Repository | 整合性・一意性・永続化上の制約 | SQL文の逐語説明 |
| View | 複雑な表示制約（例：Discord上限） | `map` / `join` の説明 |
| Listener / Interaction | イベント境界・再利用方針 | `if (isButton())` の説明 |
| Infrastructure | 外部API・DB・ファイルシステムとの境界 | SDKメソッドの説明 |
| Test | 守る契約がテスト名だけでは伝わらない場合のみ | テストコードの逐語説明 |

## 🧪 テストコメント

テスト名で意図が明確ならコメントを追加しません。
コメントが必要なのは、たとえば**インメモリDBでテスト間の共有状態を切る理由**や、**統合ルーターが10公開Commandだけを登録する契約**のような、コードから理由が読み取りにくい場合です。

## 🚧 TODO / FIXME

TODOには削除・完了条件を含めます。FIXMEは既知の不具合に限定します。

```ts
// TODO: 旧Commandの利用実績がなく、移行案内とCI契約も更新済みになったら互換層を削除します。
```

## ✅ レビュー基準

- [ ] 🎯 コメントが理由・契約・制約のいずれかを説明している
- [ ] 🔗 公開Commandと内部機能の責務が混ざっていない
- [ ] 🔁 互換層が業務ロジックを持っていない
- [ ] 📝 日本語表記と絵文字の用途が統一されている
- [ ] 🚫 同じコメントが複数箇所へ機械的に複製されていない
- [ ] 🚫 コードの逐語説明になっていない

> **コメントは「コードの翻訳」ではなく、「境界・契約・理由」を残す。** 🧠
